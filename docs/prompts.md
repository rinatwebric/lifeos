# Промпты для работы над LifeOS

Шаблоны из читшита, адаптированные под проект. Копируйте и подставляйте значения в `[...]`.

## 1. Новая фича

```text
<role>Ты senior React/TypeScript разработчик, эксперт по Supabase и продуктовым веб-приложениям.</role>

<context>
Проект LifeOS — персональная система целей, задач и планирования.
Стек: React 19, TypeScript strict, Vite, Tailwind 4, React Router 7, TanStack Query 5, Zod 4,
Supabase (Postgres + Auth + RLS). Правила проекта: AGENTS.md. Требования: docs/PRD.md §[номер].
Текущее состояние: [что уже реализовано в этом модуле].
</context>

<task>[Одно конкретное изменение, например: «добавить создание цели с этапами»]</task>

<rules>
- Следуй слоям из docs/ARCHITECTURE.md: логика не в JSX, данные через сервис фичи.
- Все даты — UTC в БД, отображение в IANA-поясе пользователя (src/lib/dates.ts).
- Обработай edge cases: пустой список, нет прав, конфликт времени, отсутствие сети.
- Никаких mock-данных в production-путях.
- Секреты только на сервере; RLS не ослаблять.
</rules>

<output_format>
План (файлы) → код → тесты → что проверено (typecheck, lint, test, build) → что осталось.
</output_format>
```

## 2. Планирование фичи

```text
<role>Ты планировщик. Код не пишешь.</role>

<context>
LifeOS, PRD: docs/PRD.md §[номера]. Текущая реализация: [модуль/файлы].
</context>

<task>Составь план реализации [фича] маленькими шагами.</task>

<output_format>
1. Требование своими словами + ссылки на разделы PRD.
2. Неоднозначности (что PRD не определяет) — вопросы.
3. Шаги по одному коммиту.
4. Файлы: новые / изменяемые.
5. Данные: таблицы, RLS, миграция, типы.
6. Тесты и команды проверки.
7. Риски и что необратимо.
</output_format>
```

## 3. Дебаггинг

```text
<role>Ты senior-разработчик. Диагностируешь методом гипотез: сначала причина, потом фикс.</role>

<bug>
Ожидаемый результат: [что ожидаю]
Фактический результат: [что получаю]
Шаги воспроизведения: [1, 2, 3]
</bug>

<evidence>
<error_log>[полный стектрейс или "нет ошибки"]</error_log>
<recent_changes>[последние коммиты / diff от рабочей версии]</recent_changes>
<already_tried>[что уже проверил и что из этого вышло]</already_tried>
</evidence>

<task>
1. Дай 3 гипотезы, отсортируй по вероятности. Для #1 объясни механизм: X → Y → Z.
2. Предложи минимальную проверку (один лог / запрос / тест).
3. Фикс — только после подтверждения причины.
</task>

<rules>
- Не предлагай фикс до подтверждения причины.
- Не оборачивай в try/catch, чтобы «скрыть» ошибку.
- Если данных мало — скажи, что ещё логировать.
- Если баг плавающий — проверь гонки, кэш, состояние между запросами.
</rules>
```

## 4. Ревью

```text
<role>Ты независимый ревьюер. Код писал не ты, контекст свежий.</role>

<context>
LifeOS. Требования: docs/PRD.md §[номера]. Правила: AGENTS.md.
Diff: [git diff / список файлов].
</context>

<task>Проверь изменения и найди проблемы.</task>

<rules>
- Проверь: соответствие PRD, отсутствие лишнего скоупа, RLS и принадлежность данных,
  отсутствие секретов во frontend, таймзоны, состояния UI (loading/empty/error/success),
  покрытие тестами, отсутствие any и дублирования типов.
- Каждое замечание: файл, строка, почему важно, конкретный фикс.
</rules>

<output_format>
Blocker / Should fix / Nit. В конце вердикт: ship / сначала блокеры / нужен план.
</output_format>
```

## 5. Правила сессии (напоминание агенту)

```text
Перед работой: прочитай AGENTS.md и нужный раздел docs/PRD.md.
Работай в пределах 30 % контекста. Одна задача — одна сессия.
Перед правками — короткий план и список файлов.
После правок — npm run typecheck, npm run lint, npm test (и build, если менялся бандл).
Сообщи, что изменил, что проверил и что осталось.
```
