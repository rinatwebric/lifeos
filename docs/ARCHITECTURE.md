# Архитектура LifeOS

Документ фиксирует принятые решения и границы слоёв. Изменения архитектуры требуют обновления этого
файла и объяснения причины (PRD §20.1).

## 1. Слои

```
UI (features/*, components/*)
        │  только рендер + локальное UI-состояние
        ▼
Хуки / сервисы (features/*/api.ts, hooks/*)
        │  TanStack Query, валидация Zod
        ▼
Supabase JS client (src/lib/supabase)  ──►  Postgres + RLS
        │
        └──► Edge Functions (AI service layer, planner)  ──►  AI provider
```

Правила:

1. Компонент не обращается к `supabase` напрямую — только через сервис/хук фичи.
2. Чистые вычисления (прогресс, overdue, слоты расписания) живут в `src/lib` и покрыты unit-тестами.
3. Серверные операции, требующие секретов (AI, планировщик) — только в Edge Functions.
4. Ошибки запросов преобразуются в понятные сообщения на уровне фичи, не в компоненте.

## 2. Принятые решения

| Решение                                                            | Обоснование                                                                            |
| ------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| Tailwind CSS 4 через `@tailwindcss/vite`, токены в `src/index.css` | CSS-first конфигурация, нет `tailwind.config.js`, темы light/dark через CSS-переменные |
| React Router 7 data router (`createBrowserRouter`)                 | Вложенные layout-роуты, будущие loaders/actions для защищённых страниц                 |
| TanStack Query для серверного состояния                            | Кеш, инвалидация, ретраи; локальный стейт только для UI                                |
| Zod для валидации env и форм                                       | Единый источник правды для типов и рантайм-проверок                                    |
| Ленивый Supabase-клиент (`getSupabaseClient()`)                    | Приложение рендерится и объясняет настройку вместо падения без `.env.local`            |
| Доменные типы в camelCase, БД в snake_case                         | Читаемый TS + точное соответствие SQL-схеме; маппинг на границе сервиса                |
| Даты: хранение UTC/ISO, отображение в IANA-поясе пользователя      | Требование PRD §11 и корректность overdue                                              |
| Overdue — вычисляемое состояние                                    | Не создаёт ложных статусов и не «портит» данные                                        |
| `calculateMilestoneProgress` возвращает `null` при 0 этапов        | UI показывает empty state вместо 0% «неудачи»                                          |
| AI возвращает proposal, а не изменение                             | Human approval обязателен (PRD §6.6)                                                   |
| Порядок этапов: `ORDER BY position, created_at, id`                | `position` не уникален (реордер без deferred-транзакций); детерминированность — чтением |
| `completed_at` не связан CHECK со статусом                         | Инвариант держит сервис (ставит/снимает вместе со сменой статуса); БД не форсит        |
| Кросс-тенантные FK закрыты RLS, не композитными ключами            | `EXISTS` в `WITH CHECK` — 6 строк без новых индексов и без зависимости от версии PG    |

## 3. Границы модулей

| Модуль               | Владеет                                        | Не делает                            |
| -------------------- | ---------------------------------------------- | ------------------------------------ |
| `features/goals`     | цели, этапы, пересчёт прогресса                | не трогает расписание                |
| `features/tasks`     | задачи, статусы, повторения                    | не размещает задачи во времени       |
| `features/planner`   | time blocks, слоты, конфликты                  | не меняет дедлайны без подтверждения |
| `features/assistant` | диалоги, предложения, применение после approve | не пишет в БД напрямую               |
| `features/analytics` | агрегаты и графики                             | не хранит собственных копий данных   |
| `lib/*`              | чистые функции и клиенты                       | не импортирует фичи и компоненты     |

## 4. Данные и безопасность

- RLS на всех пользовательских таблицах; `user_id = auth.uid()`, для `profiles` — `id = auth.uid()`.
- `user_id` никогда не принимается от клиента как аргумент доверия — берётся из JWT.
- Миграции только файлами в `supabase/migrations`; типы домена обновляются в том же коммите.
- Секреты: `SUPABASE_SERVICE_ROLE_KEY`, AI-ключи — только в окружении Edge Functions.

## 5. Тестирование

| Уровень   | Инструмент            | Что покрываем                                                          |
| --------- | --------------------- | ---------------------------------------------------------------------- |
| Unit      | Vitest                | прогресс, overdue, слоты планировщика, парсеры ответов AI              |
| Component | React Testing Library | формы, состояния loading/empty/error, подтверждения                    |
| E2E       | Playwright            | auth, создание цели и задачи, планирование, approve/reject предложения |

## 6. Деплой

- Frontend: Vercel (build `npm run build`, output `dist`), переменные `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY`.
- Backend: Supabase (Postgres, Auth, RLS, Edge Functions).
- Секреты Edge Functions — в Supabase secrets, не в репозитории.

## 7. Открытые вопросы

1. Набор статусов этапов решён (2026-11-04): только `pending | completed` —
   PRD список не задаёт, «в работе» выводится из задач этапа в Planner.
   Расширение позже — одной миграцией `CHECK`.
2. Источник часового пояса до появления профиля: сейчас — пояс браузера; после Phase 1 — `profiles.timezone`.
3. Провайдер AI и бюджет запросов — выбираются на Phase 4, архитектура провайдер-независима.
